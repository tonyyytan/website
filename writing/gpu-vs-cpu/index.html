GPUs vs. CPUs, part 1: the hardware

in progress · last updated nov 21, 2026

TL;DR

  • CPUs and GPUs are built from the same parts: ALUs, registers, pipelines and caches. What differs is the philosophy.
  • A CPU is built to make one thread fast. Pipelining, branch prediction, out-of-order execution and big automatic caches all exist so simple, sequential code runs quickly.
  • A GPU is built to keep thousands of threads busy. It groups threads into warps of 32, hides memory latency by switching between warps instead of predicting, and trades cache for enormous memory bandwidth.
  • That's the latency vs. throughput split: CPUs minimize how long one task takes, GPUs maximize how much work finishes per second.
  • Most of the hype right now is about AI inference. Generating tokens one at a time (decode) is mostly limited by memory bandwidth, not math. That's why bandwidth, low-precision formats and tensor cores matter so much.
  • The catch: a GPU only delivers if you manage all those threads and feed them data well. That's part 2 (coming soon).

0. Where I'm coming from

0.1 What I'm learning in ECE222

This term I'm taking ECE222 (Digital Computers) at Waterloo, my first real computer architecture course! It starts at binary arithmetic and the RISC-V instruction set, works up through assembly, linking and I/O, then builds a processor: the datapath, the control unit, and pipelining. It finishes with memory, from SRAM and DRAM up to caches and virtual memory. I'll walk through the parts that matter for this post in the CPU section below.

0.2 Same parts, different philosophy

"A GPU is just a CPU with thousands of cores, right?"

That's the analogy everyone uses: a CPU is a handful of expert workers, and a GPU is a warehouse full of people who can each do one simple thing. Honestly, I think it's a very accurate picture. The catch is that actually managing a thousand workers adds a lot more layers than the analogy lets on.

On a CPU, the hardware does most of that managing for you. Out-of-order execution, branch prediction and caches all exist so you can write code as if there's only one worker. On a GPU, a lot of that job comes back to you. Threads run in groups that execute in lockstep, so if half of them take a different branch, the other half wait. Memory is only fast if neighbouring threads read neighbouring addresses. Data that threads share has to be staged by hand in on-chip memory. None of these are new hardware ideas. They're the same caches, pipelines and registers, but the GPU exposes them to the programmer instead of hiding them.

So yes, it's the same parts. ALUs, registers, pipelines and memory are all things you'd recognize from a computer architecture course. But the philosophy is flipped. A CPU spends its transistors making one worker as fast as possible. A GPU spends them on more workers and trusts you to manage them.

Technical note for nerds: the "group of threads executing in lockstep" is a warp (32 threads on NVIDIA GPUs). So the analogy really should be "a thousand workers, organized into teams of 32 who all have to do the same step at the same time." That one detail changes how you write almost everything.

0.3 Why it matters

A personal note: I think this makes GPU programming a much bigger jump to start. To write fast GPU code, you have to know the hardware. And most people, me included, come in having already learned to think like a CPU programmer, so a lot of the early work is unlearning habits that were perfectly fine before.

The tooling makes the gap wider. On the CPU side, there are dozens of languages that abstract the hardware away completely. You can write Python, Java or Rust your whole career without thinking about a pipeline, and the same C code compiles for x86 and ARM. On the GPU side, most people never write a kernel at all. They use PyTorch, which calls into libraries the vendors wrote. But once you need a custom kernel, the friendliest options are tile-level languages like Triton or Pallas, which are also the closest thing to portable GPU code. But the code that really has to be fast is still mostly written close to the metal, in each vendor's own stack: CUDA for NVIDIA, HIP and ROCm for AMD, Metal for Apple, and for Intel, open standards like SYCL and oneAPI. Unlike CPU code, GPU code often doesn't move between vendors for free.

So why spend a whole post on this now? Because more and more of the world's computing is moving onto GPUs and other accelerators, and a growing share of it is AI inference: running trained models for real users, all day, every day. Training a model happens once. Serving it never stops, so every bit of efficiency turns directly into cost. And since far fewer people understand how GPUs actually work than CPUs, it's a skill that's both useful and rare.

That doesn't make CPUs obsolete. They still run the operating system, feed data to the GPU, and handle all the branchy, unpredictable logic that GPUs are bad at. The interesting question isn't which one wins. It's understanding what each one is built for, so you know where your code should run.

If you've taken a computer architecture course and wondered where GPUs fit in, this post is for you. Let's start with the CPU.

1. What is a CPU?

1.1 The datapath

Every instruction a CPU runs goes through the same five steps:

  1. Fetch: read the instruction from memory, at the address in the program counter (PC).
  2. Decode: figure out what the instruction is and read the registers it needs.
  3. Execute: do the actual work in the ALU (add, compare, compute an address).
  4. Memory: read or write data memory, if it's a load or store.
  5. Write back: put the result into a register.

The hardware that does this is the datapath: the PC, instruction memory, the register file, the ALU and data memory, with multiplexers steering data between them. The control unit reads each instruction's opcode and flips the right switches.

The simplest version does all five steps in one clock cycle. It works, but the clock has to be slow enough for the slowest instruction, so every simple add waits as long as a load. Honestly, this diagram is where computers stopped feeling like magic to me. It's just a few boxes and wires, and everything else in this section is about making it faster without changing what it does.

Keep this picture in mind, because a GPU core is built from the same basic pieces. It just has far fewer of the clever extras built around them.

1.2 Instructions, assembly, and the ISA

The instruction set architecture (ISA) is the contract between software and hardware: the list of instructions a chip promises to understand. In ECE222 that's RISC-V:

  • A load/store architecture: arithmetic only happens between registers, and memory is only touched by explicit loads and stores.
  • 32 registers, and every instruction is exactly 32 bits.
  • A handful of instruction formats, which keeps decoding simple.

So a line of C like a = b + c; becomes something like:

lw   t0, 0(s1)     # load b
lw   t1, 4(s1)     # load c
add  t2, t0, t1    # a = b + c
sw   t2, 8(s1)     # store a

Because the ISA is a stable contract, the same compiled program keeps running on newer chips for years. There are two big philosophies:

  • CISC (x86, from Intel and AMD): complex, variable-length instructions.
  • RISC (ARM, RISC-V): simple, fixed-length instructions.

The funny part is that modern x86 chips break their complex instructions into simpler RISC-like micro-ops internally, so in a way RISC won anyway.

GPUs have ISAs too, but they're mostly hidden. NVIDIA, for example, compiles to PTX, a virtual ISA, and the driver translates it into the real machine code (SASS), which changes from one GPU generation to the next. Almost nobody writes GPU assembly by hand, and you can't count on it staying the same.

1.3 Pipelining

The analogy my ECE222 course uses is laundry. Doing one load means washing, drying, folding, and putting away. If you wait for one load to be completely done before starting the next, the washer sits idle most of the time. Pipelining is just starting the next load in the washer as soon as the first one moves to the dryer. No single load gets done faster, but you finish way more loads per hour.

Latency vs. throughput: these two words come up for the rest of this post. Latency is how long one load of laundry takes, start to finish. Throughput is how many loads you finish per hour. Pipelining improves throughput without improving latency. Keep this split in mind: CPUs fight hard for low latency, and GPUs give up latency to get massive throughput.

A CPU does the same thing with instructions: each of the five steps becomes a stage, and a different instruction sits in each stage at once.

The catch is hazards, situations where the next instruction can't safely go ahead:

  • Structural hazard: two instructions need the same hardware in the same cycle. Fix: duplicate the hardware, or stall.
  • Data hazard: an instruction needs a result that isn't ready yet. Fix: forward it straight from where it was computed, or stall.
  • Control hazard: a branch, where the CPU doesn't know which instruction comes next. Fix: stall, or predict (next section).

It all feeds into one equation:

$$\text{Time} = \text{Instruction count} \times \text{CPI} \times \text{Clock period}$$

Pipelining shortens the clock period and aims for a CPI (cycles per instruction) of 1. Every hazard that causes a stall pushes the CPI back up.

GPUs pipeline too, but they handle hazards very differently. Instead of forwarding results or guessing at branches, a GPU keeps many groups of threads ready and simply switches to another group while one waits. It's a laundromat with so many customers that nobody minds if one load is stuck.

1.4 Branch prediction

Control hazards get expensive as pipelines get deeper, because by the time a branch resolves, the CPU has already started several instructions behind it. So instead of waiting, the CPU guesses:

  • A branch predictor remembers how each branch behaved recently. Loops usually keep looping, and error checks usually don't fire.
  • The CPU speculatively runs down the predicted path.
  • If the guess was wrong, it throws that work away and starts again from the right place.

Modern predictors are right the vast majority of the time on typical code, which is why an if statement on a CPU is almost free. I think this is one of the most underrated ideas in the whole course: the hardware is quietly betting on your code's behaviour, billions of times a second, and almost always winning.

Remember that, because on a GPU it isn't free. GPUs generally don't predict branches, and when threads in the same group disagree about which way to go, they have to take turns. More on that in part 2.

1.5 Out-of-order and superscalar execution

Pipelining gets you to roughly one instruction per cycle. Modern CPUs go further:

  • Superscalar: issue several instructions per cycle instead of one.
  • Out-of-order: run whichever instructions have their inputs ready, instead of strictly following program order.
  • Register renaming: remove false dependencies, where two instructions only conflict because they happen to reuse the same register name.
  • Reorder buffer: commit results in the original order, so the program still looks sequential.

This machinery is a big part of why a modern CPU core is so large and power-hungry. A lot of its area and energy goes into scheduling and bookkeeping rather than the arithmetic itself, all to find parallelism inside a single thread that the programmer never wrote down.

A GPU makes the opposite bet: it skips most of this and asks the programmer to write the parallelism out explicitly. Personally, I think that's the single biggest difference between the two, more than core counts or clock speeds.

1.6 Caches and memory

Here's the problem all those tricks run into: memory is slow. A register is about a cycle away, while main memory is hundreds of cycles away. Part of the reason is physics. ECE240 was easily the hardest course of my 2A term, but it's where it clicked for me that memory speed isn't really a design choice. It's a consequence of how the circuits physically work. Thank god most of us get to work at a much higher level than that. Still, it helps to know there are two main kinds of memory:

  • SRAM stores each bit with about six transistors wired as a tiny latch. It holds its value as long as it has power, and it's very fast. But six transistors per bit takes up a lot of chip area, so it's expensive. That's what caches are made of.
  • DRAM stores each bit as charge on a tiny capacitor, with one transistor to access it. That makes it far denser and cheaper per bit. But capacitors leak, so DRAM has to be constantly refreshed, and reading it is slower. That's what main memory is made of.

What I love about this is that the whole memory hierarchy falls out of that one tradeoff. Fast memory is expensive, so you can only afford a little of it close to the core, and cheap memory is slow, so you keep the bulk of your data further away.

Caches bridge the gap by keeping recently used data close to the core. They work because of locality:

  • Temporal locality: data you just used is likely to be used again soon.
  • Spatial locality: data next to what you just used is likely to be used next. Memory moves in cache lines, typically 64 bytes, so touching a[0] in an array of 8-byte numbers also brings in a[1] through a[7] for free.

The number to care about is the average memory access time:

$$\text{AMAT} = \text{Hit time} + \text{Miss rate} \times \text{Miss penalty}$$

For example, with a 1-cycle hit time, a 5% miss rate and a 100-cycle miss penalty:

$$1 + 0.05 \times 100 = 6 \text{ cycles}$$

So a miss rate of just 5% makes the average access six times slower. And on a CPU, all of this is automatic: the hardware decides what to keep and what to evict, and you never manage it directly.

Caches are brilliant when you reuse data. The part of ML inference we usually think of, generating text one token at a time (called decode), mostly doesn't. Generating each new token means reading essentially every weight in the model, and those weights are far bigger than any cache. The data gets used once and moves on, so the speed limit becomes how fast you can stream data from memory, not how fast you can do math. That's the first hint of why decode is memory-bound.

It also explains a lot about GPU memory. The HBM on a modern GPU is still DRAM, with the same capacitors. GPUs don't make each access dramatically faster. They stack the DRAM right next to the chip and make the connection enormously wide, so far more data flows per second. That rate, measured in bytes per second, is called memory bandwidth, and it'll matter a lot in part 2.

1.7 Multicore and SIMD: how much parallelism a CPU has

CPUs aren't purely sequential. A modern chip has two kinds of parallelism:

  • Multiple cores, each running its own thread (a thread is just an independent stream of instructions) with its own private caches.
  • SIMD (vector) units in each core, like AVX on x86 and NEON on ARM. One SIMD instruction applies the same operation to a short vector of numbers at once, say 8 or 16 floats.

Put together, a desktop CPU can do hundreds of arithmetic operations per cycle across all its cores. That's real parallelism, and well-written CPU code uses it. But it's layered on top of a design built for one fast thread. A GPU starts from the other end: thousands of lanes running the same instruction isn't an extension, it's the entire design.

1.8 The takeaway: CPUs spend their transistors on one fast thread

Step back and look at 1.3 to 1.6. Pipelining, branch prediction, out-of-order execution and caches all exist for the same reason: to make a single stream of instructions run as fast as possible, and to hide how slow memory is from the programmer. That's where a CPU spends its transistors.

The takeaway: a CPU is built to make one thread fast. Most of its complexity is there so you can write simple, sequential code and still get good performance.
Not covered here: simultaneous multithreading, prefetching, the power wall, virtual memory, cache coherence, and deeper real-world pipelines. Worth exploring if you're curious.

Now imagine taking all those transistors and spending them on more ALUs instead. Drop most of the prediction and reordering, give each core far less cache, and pack thousands of simple cores onto the chip. That's a GPU.

2. What is a GPU?

Full disclosure: I haven't taken a parallel hardware course at Waterloo yet. What follows is what I believe are the most important ideas, taught the way I'd want a course to teach them. The good news is that section 1 already did most of the work, so almost everything here is a comparison against something you've already seen.

2.1 From graphics to general purpose

GPUs were built for one job: drawing images. And drawing an image is about the most parallel problem there is:

  • A frame has millions of pixels.
  • Each pixel's colour is computed with the same math as every other pixel.
  • No pixel needs to wait for any other pixel.

So graphics hardware was designed around running the same small program on huge amounts of data at once. In the early 2000s those programs (shaders) became programmable, and people started sneaking non-graphics math into them by pretending their data was pixels. NVIDIA's CUDA, released in 2007, made that official: write general-purpose code, run it on the GPU.

This history explains almost every design decision that follows. A CPU was designed for code where parallelism is hard to find. A GPU was designed for a problem where parallelism is free.

2.2 The building block: streaming multiprocessors

↔ compare with 1.1, the datapath

A GPU isn't one giant processor. It's made of many identical blocks called streaming multiprocessors (SMs), and a big GPU has a hundred or more of them. Each SM contains:

  • Lots of simple ALUs (lanes), often called CUDA cores. They do the actual math.
  • Warp schedulers that decide which group of threads runs next.
  • A huge register file, much bigger than a CPU core's, for reasons we'll see in 2.4.
  • Shared memory, a small, fast on-chip memory the programmer controls directly.
  • Tensor cores, specialized matrix-math units (2.6).

Compare this with the datapath from 1.1. The pieces are the same: registers, ALUs, control, memory. The difference is the ratio. A CPU core has one control unit feeding a few ALUs. An SM has a handful of schedulers (four on recent NVIDIA GPUs), each feeding 32 lanes that all do the same instruction at once. The diagram shows one of them. 2.3 Warps and SIMT: one instruction, many threads

↔ compare with 1.7, SIMD

Threads on a GPU don't run individually. They're grouped into warps of 32, and every thread in a warp executes the same instruction at the same time, each on its own data. NVIDIA calls this SIMT: single instruction, multiple threads.

If that sounds like the SIMD units from 1.7, it should. Underneath, it's the same idea. The difference is in how you program it:

  • CPU SIMD: you (or the compiler) write explicit vector instructions that operate on 8 or 16 values at once.
  • GPU SIMT: you write normal code for one thread, and the hardware runs 32 copies of it in lockstep.

SIMT is a really nice illusion. Each thread looks independent, has its own registers, and can even take its own branches. But it's still an illusion, and part 2 covers what happens when threads in a warp disagree about which way to go.

2.4 Hiding latency: switch, don't predict

↔ compare with 1.3 to 1.5, pipelining, branch prediction, out-of-order

This is the part that made GPUs click for me. Remember everything a CPU does to avoid waiting: forwarding, branch prediction, out-of-order execution, big caches. A GPU does almost none of it. Each warp runs its instructions in order, and when it has to wait for memory, it just waits.

The trick is that an SM keeps many warps resident at once, often dozens. Every cycle, the warp scheduler picks any warp that's ready to go and runs it. While one warp waits hundreds of cycles for memory, others fill the gap:

Switching warps is free, and this is why the register file is so big. Every resident warp keeps all its registers on-chip the whole time, so there's nothing to save or restore. On a CPU, switching threads means the operating system saving and reloading state, which takes thousands of cycles.

This is the latency vs. throughput split from 1.3 in its purest form. Any single thread on a GPU is slow, with high latency. But the chip is almost never idle, so throughput is enormous. It's the laundromat again: so many customers that nobody minds if one load is stuck.

Occupancy: how many warps an SM can keep resident is called occupancy. It's limited by how many registers and how much shared memory each thread uses. Use too many registers per thread, and fewer warps fit, so there's less work to switch to while waiting. This tradeoff comes up constantly when tuning GPU code.

2.5 Memory: bandwidth over latency

↔ compare with 1.6, caches and memory

GPU memory follows the same philosophy. It trades latency for bandwidth:

  • HBM (high-bandwidth memory): still DRAM, with the same capacitors from 1.6, stacked right next to the GPU with a very wide connection. As of November 2026, a high-end data-center GPU has dozens of times more memory bandwidth than a typical desktop CPU.
  • Latency is not better. A single access to GPU memory takes hundreds of cycles, similar to or worse than a CPU. The GPU just hides it with warp switching instead of avoiding it.
  • Much less cache per thread. There's an L2 cache shared by the whole chip and a small L1 per SM, but split across thousands of threads, each one gets very little.
  • Shared memory is a cache you manage yourself. Instead of hoping the hardware keeps the right data close, you explicitly load a tile of data into shared memory, let a group of threads reuse it, and then move on.

That last point is the biggest change in mindset. On a CPU, caches are automatic and you mostly ignore them. On a GPU, deciding what goes into shared memory and when is a huge part of writing fast code. It's the "management" from section 0.2 made concrete.

And remember the inference punchline from 1.6: generating each token reads every weight once, with almost no reuse. That's why memory bandwidth, not raw compute, is usually the speed limit for decode, and why so much of part 2 is about memory.

2.6 Tensor cores and low-precision math

Most of ML comes down to one operation: multiplying matrices. So modern GPUs have dedicated hardware for it. A tensor core computes a small matrix multiply-accumulate (multiply two small tiles of numbers and add the result into a third) as a single operation, instead of one multiply at a time.

They go hand in hand with lower-precision numbers:

  • FP32 (32-bit float) has long been the default for ML.
  • FP16 and BF16 (16-bit) are standard for ML today.
  • FP8 and INT8 (8-bit), and even 4-bit formats on the newest chips, are increasingly used for inference.

Halving the number of bits roughly doubles how much math the tensor cores can do per cycle, and halves how many bytes you have to move through memory. Since decode is memory-bound, that second part matters just as much as the first. This connects back to the binary arithmetic from ECE222: it's the same sign, exponent and mantissa idea, just with fewer bits.

My opinion: modern data-center GPUs are really matrix machines that also happen to run general code. The latest hype is all about AI inference, and the newest chips are being designed around it. Since inference is mostly matrix multiplies, that means more tensor cores, support for ever-lower precisions, and more memory bandwidth to feed them. On the newest chips, the vast majority of the advertised compute comes from tensor cores, not the regular ALUs. The "general-purpose" part of the GPU is starting to feel like the supporting act.

2.7 The takeaway: GPUs spend their transistors on throughput

↔ compare with 1.8

Put 2.2 to 2.6 side by side with section 1, and the two philosophies are clear:

  • Where a CPU predicts and reorders to keep one thread moving, a GPU switches between thousands of threads.
  • Where a CPU has big automatic caches, a GPU has huge bandwidth and a small cache you manage yourself.
  • Where a CPU spends area on control, a GPU spends it on ALUs and tensor cores.
The takeaway: a GPU is built to keep thousands of threads busy. Any single thread is slow, but the chip as a whole does an enormous amount of work per second, as long as you give it enough parallel work and feed it data fast enough.
Not covered here: how thread blocks get scheduled onto SMs, L1/L2 cache details, multi-GPU interconnects like NVLink, graphics hardware like ray tracing units, and how designs change between generations. Worth exploring if you're curious.

That last condition is the catch, and it's what part 2 is all about. But first: what do people actually use all this throughput for?

3. What GPUs are used for (and why everyone only talks about inference)

Graphics is where GPUs started, but it's far from the only thing they're used for today. Anything that does the same math on lots of data is a good fit:

  • Graphics and gaming: still the original job, from rendering frames to ray tracing.
  • Video: encoding, decoding and editing, often on dedicated hardware inside the GPU.
  • Scientific computing and HPC: weather and climate models, molecular dynamics, fluid simulation. Most of the world's ten fastest supercomputers are built around GPUs.
  • Simulation: physics engines, robotics, and training environments for self-driving cars.
  • Data processing: GPU-accelerated databases and dataframe libraries that chew through huge tables.
  • Crypto mining: a big driver of GPU demand for a while, though it has mostly faded.
  • ML training: teaching a model by running huge batches of data through it, over and over, for weeks.
  • ML inference: running a trained model to actually answer requests.

All of these are real, and GPUs are great at every one of them. But if you read anything about GPUs today, it's almost all about the last one.

3.1 Why inference gets all the attention

It mostly comes down to money and scale:

  • Training happens once, inference never stops. A model gets trained for a few weeks or months, then served to users every second of every day for as long as it's in use.
  • It scales with users. Every message, search and generated image is another inference request. The more people use AI, the more inference there is.
  • So it's where the cost is. Every bit of efficiency, whether it's more tokens per second, fewer GPUs or less power, turns directly into money saved.

And inference cares about different things than training does:

  • Latency: a user is waiting, so how quickly the first word appears and how fast the rest streams in actually matters.
  • Memory bandwidth: as we saw in 1.6, generating each token reads every weight in the model, so decode is usually limited by memory, not math.
  • Cost per token: the number everyone is trying to push down.

That's why there's now a whole wave of chips built specifically for inference, and why lower-precision formats like FP8 and INT8 have become such a big deal. My take: GPUs were the right tool for training, almost by accident, because training looks a lot like graphics. Inference is driving a whole wave of hardware designed around AI from the ground up, and I think that's what makes this such an interesting time to be learning this stuff.
